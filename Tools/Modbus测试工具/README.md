# SAF8100 Modbus 测试工具（Windows 桌面版）

WF100E 八通道治具（PY32F002B + FreeModbus RTU 从机）的上位机测试工具。
**双击 `SAF8100 Modbus测试工具.exe` 直接用**，不需要装 Python、不需要装运行库。

---

## 1. 三步开始

| 步骤 | 操作 |
| --- | --- |
| ① 接线 | USB 转 TTL（或 485 转接板）接治具 UART，**共地**，参数固定 `115200 8N1` |
| ② 打开 | 双击 `SAF8100 Modbus测试工具.exe` |
| ③ 测试 | 顶部「连接串口」→ 点「一键测试并读取」 |

- 串口下拉框会自动定位到描述里带 `USB` / `CH340` / `CP210` 的端口（如 `COM8 — USB 串行设备`）；
  列表为空就点「刷新」，仍然为空说明驱动没装。
- 连接后点「一键测试并读取」：工具会下发 T5 任务 → 轮询进度 → 读回 8 颗芯片数据。
- 表格 8 行对应 0~7 号通道，**点任意一行**，下方「通道详情」会展开该通道所有寄存器的位域解析。

> 首次启动约 1~2 秒（自解压），之后很快；杀软若拦截请放行（PyInstaller 打包的 exe 常被误报）。

| 测试结果 | 8 通道汇总：状态、登录、错误码、增益/零点 DAC、0x45、0x4B、0x48、0x44、0x47、温度码、温度、烧写 |

## 3. 协议速查（与固件源码一一对应）

固件侧：`Src/CmdHelper.c`（命令解析）、`Drivers/FreeModbus/Modbus.c`（寄存器回调）。

### 3.1 通信参数

| 项 | 值 |
| --- | --- |
| 协议 | Modbus RTU 从机 |
| 从站地址 | 1（`product.h: MODBUS_ADDRESS`） |
| 串口 | 115200 8N1 |
| 命令通道 | 写保持寄存器，**PDU 地址 40000**（逻辑 40001 起） |
| 结果通道 | 读输入寄存器，**PDU 地址 30000**（逻辑 30001 起） |
| 超时 / 重试 | 500 ms / 2 次（任务轮询用 400 ms / 0 次） |

### 3.2 ⚠️ 地址为什么是 40000 / 30000，而不是 0

固件用的 FreeModbus 在 `mbfuncholding.c` / `mbfuncinput.c` 里会先做：

```c
usRegAddress = (pucFrame[ADDR_OFF] << 8) | pucFrame[ADDR_OFF + 1];
usRegAddress++;                       /* ← 这里 +1 */
eMBRegHoldingCB(..., usRegAddress, ...);
```

而回调判断的是：

```c
if ((usAddress == 40001) && ...)      /* Modbus.c: eMBRegHoldingCB */
if ((usAddress == 30001) && ...)      /* Modbus.c: eMBRegInputCB  */
```

所以主站 PDU 里必须填 **40000 / 30000**，从机 +1 之后正好等于 40001 / 30001。
工具默认就是这个值；若换成标准 0 基从机（普通 PLC），在「手动指令 → 地址基准」切到 `0 / 0`。

### 3.3 命令表

| 功能 | 写入（40001 起） | 回读 | 返回（30001 起） |
| --- | --- | --- | --- |
| 读版本 | `1, 0x104` | `FC04 × 16` | ASCII，拼成 `8100 v1.0` |
| 总电源 | `1, 0x201, dp` | `FC04 × 1` | 1 = 设置成功 |
| 下发任务 | `5, 0x77, 任务号, 掩码, 0, 0, 0` | — | 任务立即启动 |
| 查状态 | `5, 0x66` | `FC04 × 7` | busy, order, prog, paras0..3 |
| 读测试数据 | `5, 0x610, 起始通道` | `FC04 × 8×N` | 每颗芯片 8 个寄存器 |
| 写芯片配置 | `5, 0x780, 0, gd, zd, pga, pctrl, adc, sys, lut, flags` | `FC04 × 1` | 1 = 已写入 |

- 任务号：`5` 全流程测试 / `6` 快速测温 / `7` OTP 烧写（**不可逆**，工具会二次确认）
- 通道掩码：bit0~bit7 对应 0~7 号通道，`0x00` 与 `0xFF` 都是「全部」
- 所有写命令必须用 **FC10 从 40000 一次写完**：固件在 `eMBRegHoldingCB()` 的 `MB_REG_WRITE`
  分支里调用 `Parse()`，用 FC06 只写一个寄存器是拼不出命令的

### 3.4 `0x610` 数据布局（每颗芯片 8 个 16 位寄存器）

| 偏移 | 内容 | 拆分 |
| --- | --- | --- |
| +0 | login / err | 高字节 = 登录应答（0x55 正常），低字节 = 错误码 |
| +1 | act_gd | 增益 DAC，0~0x3FFF |
| +2 | act_zd | 零点 DAC，0~0x3FFF |
| +3 | pga_gain / adc_ctrl | 高字节 = 0x45，低字节 = 0x4B |
| +4 | pga_ctrl / sys_ctrl | 高字节 = 0x48，低字节 = 0x44 |
| +5 | lut_sel / fuse_done | 高字节 = 0x47，低字节 = 烧写完成标志 |
| +6 | temp_code | 温度原始码 |
| +7 | temp_x100 | 温度 ×100，**有符号**（0x0DAC = 35.00 ℃） |

长度上限：`sendBuf` 共 120 个寄存器 → 一次最多 15 颗，本治具 8 颗一次读完（64 个）。

错误码：`0x00` 正常 / `0x01` 登录失败 / `0x02` OWI 通信失败 / `0x03` 回读不一致 /
`0x04` OTP 烧写失败 / `0xFE` 本通道未参与本次测试（被掩码跳过）。

温度换算：`T(℃) = (temp_code − 32383.8) / 114.2`

### 3.5 配置位域

```
0x45 PGA_GAIN = (G1 << 5) | (G3 << 2) | G2
0x4B ADC_CTRL = (OSR << 3) | AVG_NUM
0x48 PGA_CTRL = (VREF_SEL << 7) | (REF_GAIN << 6) | (SPIN_CLKS << 2) | VCM_SEL
```

官方 demo 默认值：`act_gd=10000`、`act_zd=16383`、`0x48=0x43`、`0x4B=0x15`、`0x45=0x52`
（工具里点「官方默认值」即可恢复）。

`0x44` / `0x47` 默认**不写**（避免清掉芯片内已有校准位），只有勾选
「额外写 0x44/0x47 (ext_en)」才会写入 —— 对应 `flags` 的 bit1。

> 注意：固件里 `0x780` 的参数从 `cmd[3]` 开始取，所以命令块第 3 个寄存器（`cmd[2]`）是占位，
> 实际 `act_gd` 在 `40004`。工具已按代码实现。

## 4. 常见问题

### 4.1 一个字节都不回？先做这两步（30 秒定位）

「更多工具 → 手动指令 / 调试」里有两个诊断按钮，能把问题一刀切成两半：

1. **回环自测**：把适配器的 **TX 和 RX 直接短接**（不接治具），点这个按钮。
   - 日志显示 `回环通过` → 串口、驱动、适配器、波特率全部正常，问题在**适配器往后的接线或从机**
   - 显示 `回环无回传` → 串口选错 / 驱动异常 / 适配器坏，与治具无关
2. **监听 3 秒**：接上治具，给治具**重新上电**的同时点它。
   - 收到任何字节 → 线是通的（从机平时不回包，静止属正常）
   - 全程 0 字节 → TX/RX 没交叉、没共地，或治具没上电/没跑这版固件
3. **读长度扫描**：读 30001 起 8→120 个寄存器，逐个试，量出从机**最长能回多长**。
   若只有长帧失败（短帧正常），就是从机发长报文时丢字节，不是接线问题。
4. **写长度扫描**：发 13→39 字节的 FC10 写命令（内容都是"查状态 0x66"，不改设备状态），
   量出从机**最长能完整收到多长**。这条是**PC→从机方向**的判据：
   - 只有 ≤19 字节能收到、20 字节以上收不到 → 就是固件判帧太短，
     典型是"USB 转串口把一帧拆成几个包 + 从机按 1.75ms 判帧"，
     把 `porttimer.c` 里的 `MB_T35_TICKS` 放大（默认 8 ≈ 14ms）即可
   - 一直到 39 字节都正常 → PC→从机方向没问题，去查从机→PC 方向

> 读取数据时按 **2 颗一段**（16 个寄存器 / 37 字节应答）读，每段最多重试 3 次；
> 仍然读不到的段会**再降级为逐颗读**（8 个寄存器 / 21 字节应答），
> 短帧丢字节概率低得多。全部失败的通道标 `0xF1 读取失败`，不会拖垮整轮。

### 4.2 固件版本对照（烧完请用「读版本 0x104」确认）

| 版本 | 内容 |
| --- | --- |
| v1.0 | 原始 |
| v1.1 | 修 T3.5 判帧（改为静默计数）+ UART 发送不再用阻塞 HAL |
| v1.2 | 栈 0x400→0x5F0，避免 `ucRTUBuf` 尾部被栈踩 |
| v1.3 | 两处 `__HAL_UART_CLEAR_PEFLAG` 加 `RXNE==RESET` 守卫（该宏会读 DR，会把刚到的字节吃掉）；`PutByte` 先等 TXE |
| v1.4 | 判帧静默 `MB_T35_TICKS=8`（约 14ms），兼容 USB 转串口拆包 |
| v1.5 | 列电源独占（先关 4 列再开本列）；新增 `0x6A0` OWI 探测命令 |
| v1.6 | 判帧静默 8→20 tick（35ms）；新增 `0x6A1` 通信质量计数（CRC 错帧/串口溢出/帧内最大间隔） |
| v1.7 | **修 `0x6A0` 探测把 MCU 卡死**：`power_cycle()` 在中断里用了 `HAL_Delay`，改为 TIM1 轮询延时 |

工具侧：v1.7 起每段重试 5 次，并新增「链路自检」按钮。

### 4.3 OWI 探测（0x6A0）：一条命令分清"没电 / 没接 / 坏片"

「手动指令 / 调试」最下面的蓝色按钮 **OWI 探测（逐通道）**，会按当前通道掩码逐颗执行：
断电 100ms → 上电 20ms → 发 `F3 A0` 登录，然后把固件内部的原始数据读回来。

日志判读：

| 日志 | 含义 | 下一步 |
| --- | --- | --- |
| `登录成功 0x55` | 该颗通信正常 | 可以跑一键测试 |
| `相位 0，VDD脚=0` | 该列 VDD 使能脚没打开 | 查 `0x201` 总电源、`U9` 输入、列开关 |
| `相位 0，VDD脚=1，总线=1` | 有电，但芯片完全不拉线 | 芯片没插好 / 方向反 / OWI 线断 / 该位没片 |
| `相位 0，VDD脚=1，总线=0` | OWI 线被拉死 | 短路、芯片损坏 |
| `相位 >0 但登录失败` | 芯片应答了，但解码不过 | 查上拉电阻、位时序（首相位低/高宽度会打出来） |

`0x6A0` 参数 = 通道号，返回 8 个寄存器：`[0]` 高字节登录应答/低字节相位数、
`[1]` 高字节 VDD 脚电平/低字节 OWI 空闲电平、`[2..7]` 前三个相位的低/高宽度（us）。

### 4.3.0 链路自检：先确认线是不是好的

主界面「测试数据」卡片里的 **链路自检** 会连发 20 条 8 字节读命令，直接给出成功率：

- `≥95%`：链路好，可以查业务问题
- `70~95%`：偶发丢字节，配合「通信质量」判断是线还是 MCU
- `<70%`：**先修线**。本板通信是 **RS485**（U12 = TD301M485 隔离模块，PB4/PB5 → 模块 → A/B 端子），
  转接器必须接 **A/B 端子**并与板子共地；如果误接在 PB4/PB5 的 TTL 侧，会和模块互相驱动，必然乱码

判据：如果坏帧的**帧尾两字节仍是正确 CRC**，但中间/帧头少了字节 → 线上丢字节（电气层）；
如果整帧 CRC 校验失败且帧尾也不对 → 字节被改写（干扰）。

### 4.3.1 通信质量（0x6A1）：命令为什么会"无应答"

主界面「测试数据」卡片里的 **通信质量** 按钮，读从机上电以来的累计计数：

| 计数 | 说明 |
| --- | --- |
| 正确帧 / CRC 错帧 | 从机收到并校验通过的帧数 / 校验失败被丢弃的帧数 |
| 收字节 | 收到的字节总数 |
| 溢出 | **串口溢出次数**——CPU 没及时取数据，硬件丢字节 |
| 帧内最大间隔 | 一帧内部两个字节之间最大的停顿（tick，1 tick = 1.75ms） |

判读（工具会自动给结论）：

- `溢出 = 0`、`CRC 错帧 > 0`、`最大间隔 ≥ 3 tick` → 线上字节不连续，USB 转串口拆包；把 `MB_T35_TICKS` 继续加大
- `溢出 > 0` → 从机 CPU 没及时取数据，硬件丢字节（与上位机无关）
- `CRC 错帧 = 0` → 链路干净，问题不在通信

### 4.4 关于"分段读了 8 段，但每段数据一模一样"

如果某一轮 8 个通道全是 `err=0xFE`（未测试），那么每颗芯片回的都是同样的
`00 FE 00 00 ...`，分段读看起来就会"全一样"。这不是起始通道参数失效，
判别方法是看**跑过测试之后**的数据：真实测量值每颗都不同
（例如 `5500 2710` / `5500 2716` / `5500 271C`），那时分段读的差异一眼可见。

排除法顺序（命中率从高到低）：

1. **串口选错**：拔掉 USB 转接器 → 点「刷新」→ 消失的那个 COM 才是它。
   （电脑上常有一堆蓝牙虚拟串口，`USB 串行设备` 才是转接器）
2. **TX/RX 没交叉**：适配器 TX → 单片机 RX（PB5），适配器 RX → 单片机 TX（PB4），**GND 必须共地**。
3. **电平/接口类型不对**：治具是 3.3V TTL 就接 TTL 转接器；若是 RS485，A/B 不能接反，
   且确认是自动收发的 485 芯片（否则固件没有方向脚，从机发不出去）。
4. **从机没跑起来**：治具没上电、固件没烧、或烧的还是旧 SOP100E（JH1101）那一版。
5. **波特率**：固定 115200 8N1，两端必须一致。

> 判据：固件对地址不对、CRC 错这类问题**会回异常帧**（`01 90 02 ...`）。
> 现在 RX 完全是空的，说明报文根本没被对端收到，先别怀疑命令内容。

| 现象 | 原因 / 处理 |
| --- | --- |
| TX 有日志、RX 一个字都没有 | 见 4.1；先回环自测再监听 |
| 收到的回包 CRC 错 / 半包 | 波特率不匹配、线太长、地线不良、或 485 方向切换慢 |
| --- | --- |
| 双击没反应 / 秒退 | 先确认是 64 位系统（Win7 SP1 及以上）；被杀软拦截时加白名单 |
| 串口列表为空 | 装 CH340 / CP210x 驱动；换 USB 口；点「刷新」 |
| 全部命令报「从机异常码 0x02」 | 地址基准不对：切到 `0 / 0` 试；或从站地址不是 1 |
| 全部超时 | 波特率不是 115200、TX/RX 没交叉、没共地、线只供电 |
| 只有部分通道有数据 | 掩码只选了一部分；或该通道空片（`0x02` = OWI 无应答） |
| 表格里「未测试」 | 该通道被掩码跳过，固件把 `err` 置 `0xFE` |
| 日志出现「状态查询无应答…继续等待」 | 正常：固件在 OWI 通信期间会关掉 Modbus 时基中断（TIM14），几十毫秒内不应答 |
| 任务一直 busy | 正常，8 通道全流程约 4~6 s，T7 烧写更久（上限 120 s） |
| 端口被占用 | 关掉其它串口工具（Modbus Poll、串口助手）后重连 |
